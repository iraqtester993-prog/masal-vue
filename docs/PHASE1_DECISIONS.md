# قرارات الدفعة الأولى وما يحتاج تثبيتًا

تحديث الدفعة التالية، 2026-10-06: الإصدار الفعّال على بوابات staging الثلاث هو `20261006-accounts-02` للحسابات والموظفين والصلاحيات والمرفقات. سجل الأساس أدناه تاريخي؛ [دليل الدفعة الجديدة وحدودها](ACCOUNT_PHASE2_VERIFICATION.md). النطاق الرئيسي والإنتاج النهائي وبقية وحدات الأعمال لم تطلق.

التاريخ: 2026-10-06، توقيت بغداد. يقرأ مع `PORTAL_ARCHITECTURE.md` و`PERMISSION_MATRIX.md` و`FEATURE_INVENTORY.md`. الغرض منع تحويل افتراض مؤقت إلى قاعدة تجارية معتمدة دون مراجعة.

## ما قرره المستخدم

| القرار | أثر التنفيذ |
|---|---|
| Vue للواجهة وLaravel للباك | اعتماديات وبناء واختبارات مستقلة |
| ثلاث بوابات منعزلة | مدير، وكلاء، نقاط بيع؛ ليست صفحة دخول موحدة |
| الرئيسي والفرعي والفرع الفرعي في بوابة الوكلاء | بوابة مشتركة، ومحتوى وصلاحيات حسب الحساب |
| نقطة البيع يمكن أن تتبع أي مستوى وكيل مباشرة | يسمح تحت الرئيسي أو الفرعي أو الفرع الفرعي، دون إلزام المرور بجميع المستويات |
| إنشاء التابع داخل نطاق المنفذ وفق نوع الأب المختار | المدير داخل النظام، والوكيل تحت نفسه أو تابعيه مع account.create؛ نقطة البيع لا تنشئ حسابات |
| الحساب يدير نفسه وتابعيه المصرح لهم | فرض النطاق في السيرفر، لا في قوائم Vue فقط |
| إزالة الاعتماد على الخزن المحلي | الحالة الجديدة مؤقتة في الذاكرة، والمصادقة بجلسة سيرفر |
| المصدر داخل مجلد المشروع الحالي | `frontend/backend/contracts/docs/deployment` |
| أخذ نسخة احتياطية وخطة متابعة | النسخ خارج المصدر، والإنجاز موثق بدليل تحقق |

## افتراضات آمنة للأساس فقط

| الافتراض | السبب وحدود العمل |
|---|---|
| قاعدة بيانات واحدة وعزل منطقي | أبسط للصيانة؛ لا يفترض قواعد مستقلة لكل وكيل |
| مستخدم بعضوية فعالة واحدة في عملية الدخول | الانتقال بين عضويات متعددة مؤجل؛ لا اختيار `account_id` من العميل |
| أدوار النظام والوكلاء الافتراضية تملك `account.view` و`account.create`؛ نقطة البيع تملك العرض فقط | لا بيع أو تحويل أو منح صلاحيات مخصصة ضمن هذه الدفعة |
| نوع الحساب يحدد بوابة الدخول | نوع الموظف لا يفتح بوابة خارج نوع حساب عضويته |
| الحساب غير الفعال أو السلسلة غير الفعالة ممنوعان | منع وصول مبكر محافظ؛ استثناءات الدعم والتعطيل الجزئي تحتاج قرارًا |
| سجلات خارج النطاق تعامل كغير موجودة | لا تكشف قائمة أو تفاصيل عن شبكة أخرى |
| لا حسابات عرض في الإنتاج | Fixtures للاختبارات، ومدير الإنتاج ينشأ بأمر إداري دون كلمة مرور ثابتة |
| إنشاء تابع مسموح فقط بالنوع الموافق لأب داخل النطاق | إنشاء العلاقات ذري؛ نقل التبعية والتعديل على العلاقات لا يزالان غير متاحين |
| لا بيانات مستوردة من المتصفح تلقائيًا | لا تحويل بيانات مالية غير مفحوصة إلى قاعدة الإنتاج |
| نفس النطاق للواجهة والـAPI في كل بوابة | جلسات مضيف مستقلة ولا CORS عابر للنطاقات لهذه الدفعة |

إذا غيرت قاعدة لاحقًا، توثق بتاريخها وأثرها على البيانات والاختبارات قبل تنفيذ مسار جديد. لا تنشئ مرحلة الأساس معاملات مالية أو تنقل أرصدة أو تحذف بيانات متصفح. حساب التابع يأتي مع مستخدمه الأول؛ الدور والحالة وصلاحيات البداية يحددها السيرفر، وكلمة المرور لا تدخل الاستجابة أو السجل.

## أسئلة العمل المعلقة

هذه أسئلة سجل مرحلة الأساس. ثبتت قواعد الإيقاف والموظفين والتفويض في الدفعة الثانية ضمن [مصفوفة الصلاحيات](PERMISSION_MATRIX.md) و[مراجعة المطابقة](ACCOUNT_PHASE2_PARITY.md)؛ الأسئلة المتبقية تخص المجالات أو الاستثناءات غير المنقولة:

1. قواعد هذه الدفعة محسومة: المخول يدير التابع داخل نطاقه، الموظف لا يتجاوز نوعه وسقف المالك ومنع الأعلى، وإنشاء الحساب وتغيير معرف الدخول مقيدان بالمالك. التفويض المالي وتفويض المنتجات يحتاجان قواعد وحداتهما.
2. إيقاف الأب يمنع دخول وتشغيل تابعيه ويسحب جلساتهم، مع بقاء الإيقاف المستقل للطفل عند تفعيل الأب. استثناء دخول دعم مقيد أو تعليق عمليات مالية بعينها لم ينفذ.
3. هل يمكن للشخص العمل في عدة حسابات؟ كيف ينتقل بينها وهل يحتاج جلسات مستقلة؟
4. هل المدير أو الرئيسي يبيع مباشرة؟ المصدر القديم يقيد بعض عمليات البيع بهيكل مختلف؛ لا يعتمد كقرار جديد.
5. من يحدد سعر كل مستوى، ومن يعتمد تغييره، ومتى يثبت السعر في البيع؟
6. هل الأب يرى تكلفة التابع وربحه ورموز بطاقاته ووثائقه؟ هذه صلاحيات حقول مستقلة.
7. ما حدود الرصيد والائتمان والتحويل والاسترجاع وإعادة الطباعة؟
8. كيف تنقل تبعية الحساب، وما مصير مخزونه وأرصدته والسجلات القديمة؟
9. هل في المتصفحات بيانات حقيقية يجب أرشفتها أو ترحيلها قبل تنظيف مفاتيح ماسال؟
10. ما الأجهزة والطابعات ومزودو الخدمات الذين نحتاج ربطهم؟
11. ما عدد المستخدمين المتزامنين والبطاقات والعمليات اليومية المتوقع؟

## ملاحظات من قراءة المصدر السابق

- المصدر السابق يميز `owner/main/sub/pos/employee/supervisor`، ويستدل على الفرع الفرعي من الأب. النوع الجديد `sub_branch` صريح.
- `legacy/src/services/access.js` يحتوي منعًا صلبًا للبيع والخدمات الرقمية لبعض الأدوار، وقواعد تفويض تتجاوز قائمة الصلاحيات الافتراضية. نقل القائمة وحدها يفقد هذه القواعد.
- `legacy/src/services/network-accounts.js` يطبق قواعد إنشاء وتفويض محليًا، و`engine.js` ينفذ عمليات في المتصفح. نقلها يحتاج خدمة Laravel واختبارًا لكل قاعدة، لا مجرد طلب API.
- `legacy/src/services/state-storage.js` يحفظ حالة النظام في `localStorage`. حفظ المصدر كمرجع لا يجيز تحميله في التطبيق الجديد.

قوائم الحصر السابقة تبقى مفيدة، لكن المسارات `src/...` الواردة فيها تشير الآن إلى المصدر المرجعي تحت `frontend/legacy/src/...`.

## ما لا ندعي اكتماله

نشر أساس Vue/Laravel فعليًا على نطاقات التجربة الثلاثة، مع migrations والأدوار على قاعدة MariaDB مستقلة. نجحت اختبارات الأساس المحلية وفحوص المعاملات على قاعدة الاستضافة ودخول المدير وخروجه وإعادة دخوله وعزل جلسته عبر HTTPS. الأدلة الدقيقة وحدودها في [FOUNDATION_VERIFICATION.md](FOUNDATION_VERIFICATION.md) و[HOSTING_READINESS.md](HOSTING_READINESS.md)؛ اكتمال كل بند يسجل منفصلًا في ملف الخطة.

لم تثبت جميع قواعد عمل الإنتاج، ولا دعم استضافة جميع الوظائف، ولا توفر Queue Worker أو SMTP أو موارد الأحمال. نطاقات الإنتاج ما زالت مقترحة، والنطاق الرئيسي لم يستبدل بالمشروع. استعادة نسخة DB والرجوع إلى إصدار سابق وكامل وظائف الأعمال لا تزال تحتاج التنفيذ والتحقق؛ نجاح staging لا يغلق هذه البنود.
