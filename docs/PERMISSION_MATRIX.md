# الصلاحيات والنطاق — مرجع المصدر وقرار الانتقال

التاريخ: 2026-10-06. هذا الملف يميز أساس السيرفر المنفذ عن السلوك المرجعي القديم والسياسات التجارية المعلقة؛ نشر الأساس في staging لا يعني اعتماد سياسة الإنتاج لكل المجالات.

قرار المستخدم النهائي: ثلاث بوابات admin وagents وpos، والوكلاء الرئيسيون والفرعيون والفرع الفرعي يستخدمون agents بنطاقات حساب مختلفة. المصادقة والجلسات مستقلة بين المضيفين. مصدر التنفيذ القديم انتقل إلى `frontend/legacy/src`؛ إشارات src أدناه تخص ذلك المرجع.

الأساس المنشور أولًا يشمل login/logout/me وقراءة الحسابات وإنشاء التابعين؛ دليله في [FOUNDATION_VERIFICATION.md](FOUNDATION_VERIFICATION.md). توسعة المصدر الحالية تضيف التعديل والإيقاف والصلاحيات والموظفين وأنواع الصلاحيات والمرفقات، ونُشرت بالإصدار `20261006-accounts-02`؛ دليلها في [ACCOUNT_PHASE2_VERIFICATION.md](ACCOUNT_PHASE2_VERIFICATION.md). نقل التبعية والمالية وبقية المجالات مؤجل. الفروق مع الأصل في [ACCOUNT_PHASE2_PARITY.md](ACCOUNT_PHASE2_PARITY.md).

## نطاق المصدر الحالي وحدود هذه الدفعة

تحديث الدفعة الثالثة: الإصدار الفعّال `20261006-catalog-03`؛ كتالوج السيرفر يحتوي **38 مفتاحًا منفذًا**. [أدلة الشركات والفئات وإتاحة التابعين](CATALOG_PHASE3_VERIFICATION.md). الجدول القديم في PERMISSION_CATALOG مرجع للمصدر، وليس قائمة صلاحيات تنسخ تلقائيًا.

| إجراء القاموس | أذون السيرفر والنطاق |
|---|---|
| عرض الفئات والصور | `account.view` و`products.view`؛ owner يرى فئات مسار حسابه، والموظف اتحاد فئات جذوره المصرح بها؛ خارج الشبكة 404 |
| إدارة الشركات | `providers.view` مع create/edit/toggle/export/images بحسب الفعل، وحساب النظام داخل نطاق الموظف؛ الوكيل لا يعدل القاموس المركزي ولو منح مفتاحًا |
| إضافة/تعديل/تفعيل/ترتيب فئة | `products.view` مع create/edit/toggle/order؛ إدارة النظام داخل النطاق فقط؛ version وقفل DB وتدقيق داخل معاملة |
| تغيير بيانات البطاقة/الصورة/المحافظات | `products.fields` و`products.images` و`products.availability` على الترتيب، إضافة إلى إذن الفعل؛ الحقل المحمي غير المعدل يحتفظ بقيمته |
| تصدير فئات | `products.view` و`products.export` و`data.cost`؛ نفس نطاق وفلاتر القائمة، حد 10000، CSV محمي من الصيغ؛ لا رموز بطاقات فعلية |
| تحديد فئات تابع | owner أعلى في الشبكة مع `account.view` و`agents.categories`؛ لا الذات ولا النظام ولا موظف، وversion + catalog_version؛ لا إلغاء منع الأسلاف |
| اختيار أعمدة | عرض الفئات؛ تفضيل المستخدم نفسه محفوظ في DB، والاسم والإجراءات لا يخفَيان |

وفق بوابة الوكلاء المشتركة المطلوبة، الرئيسي والفرعي والفرع الفرعي يحصلون افتراضيًا على عرض/تصدير الفئات داخل الإتاحة المصرح بها؛ توسعة عرض الفئات للفرعيين فرق مقصود عن عينة كتالوج المصدر التي اقتصرت على الرئيسي. POS لا يحصل على إدارة القاموس المركزي. موظفو كل مستوى يعتمدون على نوع الصلاحية والنطاق الحي؛ لا ينسخون أذون owner دون تفويض.

| نوع الحساب | نطاق البيانات | الإدارة |
|---|---|---|
| مدير النظام (`system`) | جميع الحسابات مع إذن العرض | إنشاء تابع وإدارة الحسابات والموظفين والصلاحيات بالنطاق والإذن؛ لا تعديل حساب النظام من APIs التابع |
| وكيل رئيسي (`main_agent`) | الذات وكل descendants الفعليين | إنشاء تابع تحت نفسه أو أب داخل شجرته، وإدارة التابع بالإذن؛ لا الشبكات المستقلة |
| وكيل فرعي (`sub_agent`) | الذات وكل descendants الفعليين | إنشاء وإدارة تابع داخل شجرته بالإذن؛ لا قراءة الأب أو الإخوة خارج النطاق |
| فرع فرعي (`sub_branch`) | الذات ونقاط البيع التابعة | إنشاء POS وإدارة نقاطه بالإذن داخل شجرته |
| نقطة بيع (`pos`) | حسابها فقط | عرض حسابها ومرفقاته وإدارة موظفيها وأنواع صلاحياتهم بالإذن؛ لا إنشاء أبناء أو تعديل الحساب التجاري، والبيع لم ينقل |
| موظف (`employee`) | جذور صريحة، مع اختيار descendants وتقاطعها مع شجرة صاحب العمل | نوع صلاحية نشط مقاطع حيًا بصلاحيات صاحب الحساب؛ لا إنشاء حساب تجاري أو تعديل معرف تابع ولو مُنح مفتاحهما |

الفصل المطلوب: account type مستقل عن user role. الاستثناءات والعضويات لا تمنح نطاقًا خارج الشجرة دون إجراء مركزي مصرح ومدقق.

## مصفوفة المصادقة والحسابات

| الإجراء | فحص السيرفر | الحدود |
|---|---|---|
| `POST /api/v1/auth/login` | هوية صحيحة بعضوية واحدة، مستخدم/عضوية/حساب/أسلاف فعالون، سلسلة closure كاملة، والبوابة توافق نوع الحساب؛ تحديد معدل المحاولات | اختيار بوابة/دور/حساب من body؛ الدخول بهوية صحيحة عبر بوابة حساب أخرى |
| `GET /api/v1/auth/me` | الجلسة تنتمي لبوابة المضيف، وسلسلة النشاط والصلاحيات تعاد قراءتها | استعادة صلاحيات ثابتة من Vue أو قبول هوية لبوابة أخرى |
| `POST /api/v1/auth/logout` | جلسة مرتبطة بالبوابة وحماية الطلب | يبقى الخروج متاحًا بعد تعطيل الحساب أو العضوية؛ لا يتطلب إذن أعمال |
| قراءة قائمة/تفاصيل الحسابات | `account.view` ونطاق query قبل القراءة؛ pagination؛ خارج النطاق 404 | قراءة أب أو أخ أو شبكة مستقلة لوكيل/POS، أو إرسال كل الشبكات ثم فلترتها في المتصفح |
| `POST /api/v1/accounts` | عضوية owner و`account.create` وأب داخل نطاق القراءة والنوع الموافق؛ تحقق الحقول؛ account/user/membership/closure/audit في transaction واحدة | role/status/permissions من العميل، نوع غير مسموح، أب خارج النطاق، أو إنشاء نصف حساب عند فشل أي جزء |

## أذون توسعة الحسابات والموظفين

هذه مصفوفة الدفعة المنشورة؛ تحققها في اختبارات المصدر وHTTP وMariaDB والمتصفح موثق في سجل الدفعة الثانية، ولا يثبت نقل المالية أو المنتجات.

| الإجراء | أذون السيرفر والقيود |
|---|---|
| تعديل بيانات التابع | `account.update`، target scoped غير الذات والنظام، version؛ لا type/parent/role/password؛ حقول POS للجهاز تحتاج `pos.device` والموقع `pos.location` |
| إيقاف/تفعيل التابع | `account.toggle`، نفس حدود التابع مع reason/version؛ إيقاف الأب يسحب جلسات الشجرة، وإعادته لا تمحو إيقافًا مستقلًا لطفل |
| معرف دخول التابع | `account.login` وowner في حساب system فقط؛ identifier واحد بريد أو username، يمحو البديل ويسحب الجلسات |
| صلاحيات التابع | `account.permissions`، target scoped غير الذات والنظام، reason/version؛ مفاتيح معروفة ضمن actor/type/ancestor ceiling وطبقة السلطة |
| قائمة الموظفين/إضافتهم | `staff.view` / `staff.create`؛ سياق الحساب ثابت، employee فقط، profile نشط وجذور غير فارغة داخل employer وactor scope |
| تعديل الموظف | `staff.update`؛ تعديل profile يحتاج `staff.role`، وتعديل الجذور/descendants يحتاج `staff.scope`؛ owner والذات محميان ولا تبديل account أو role |
| إيقاف الموظف | `staff.toggle` وreason/version؛ protected owner والذات مرفوضان، والإجراء يسحب الجلسات |
| أنواع الصلاحيات | `permission_profile.view/create/update/toggle/delete` لكل فعل، وview لإجراءات الإدارة؛ نوع المنفذ أو أعضاء خارج سلطته محميون؛ حذف مرتبط409 |
| قراءة/إدارة الصور | `account.attachments.view` للقراءة؛ الرفع والحذف يحتاجان `account.attachments.manage` و`account.update` لتابع؛ التخزين خاص والتنزيل scoped |
| اسم المالك الحالي | `PATCH /auth/profile` بعضوية owner وmembership.version؛ name فقط؛ البريد وكلمة المرور يحتاجان مسارًا مستقلاً لاحقًا |

نوع الحساب لا يساوي نوع عضوية المستخدم. System employee لا يصبح owner. موظف لا يحصل على نطاق شامل عند roots فارغة، ولا على كامل شجرة الوكيل تلقائيًا. POS يملك افتراضيًا أذون موظفيه وأنواع صلاحياتهم ومشاهدة مرفقاته؛ موظفوه يبقون داخل سياقه. المنع الحالي يراجع في كل طلب، وإصدار جلسة السيرفر يبطل ملفات الجلسة القديمة بعد السحب.

قرارات `account_permission_rules` تنسب السلطة إلى حساب المنفذ في السيرفر. الأدنى لا يمحو منع الأعلى؛ تغيير الأعلى نفس target/key يستبدل الأدنى للمفتاح المتغير فقط. استعادة إذن الأب لا تمحو منعًا مستقلاً محفوظًا على طفل. لا يقبل API authority_id أو خارطة استثناءات مزورة.

`grantable_permissions` و`profile_grantable_permissions` خيارات محسوبة للواجهة، وليستا إذنًا يرسل العميل إثباته. Server يعيد التحقق عند الحفظ. هوية owner تظهر في detail/mutation وcreate، وتُحذف من index؛ كلمات المرور والهاش والtokens ومسار ملف خاص لا تدخل Resource.

إنشاء الحساب مربوط بسياق الأب في الجدول. يستطيع الرئيسي، مثلًا، إنشاء فرع فرعي تحت وكيل فرعي تابع له داخل شجرته؛ لا يلزم أن يكون الأب المختار حساب المنفذ نفسه.

| نوع الأب | أنواع الأبناء المسموحة |
|---|---|
| `system` | `main_agent` |
| `main_agent` | `sub_agent` أو `pos` |
| `sub_agent` | `sub_branch` أو `pos` |
| `sub_branch` | `pos` |
| `pos` | لا أبناء |

نقطة البيع تحت أي مستوى وكيل قرار معتمد من المستخدم. المستخدم له عضوية واحدة في المرحلة الأولى مع قيد قاعدة بيانات؛ تعدد العضويات واختيارها مؤجلان.

تعطيل المستخدم أو العضوية أو الحساب أو أي سلف، أو سلسلة closure ناقصة، يمنع الدخول والوصول للبيانات. محاولة الدخول تعطي فشلًا عامًا 422. الجلسة المسحوبة تمنع بـ401، والجلسة ذات بوابة/عضوية غير مسموحة أو حالة غير فعالة قد تمنع بـ403؛ الخروج يبقى متاحًا للبوابة المرتبط بها. هذه سياسة النشاط المحافظة؛ أضيف API الإيقاف والتفعيل العام، بينما استثناءات الدعم وإيقاف أعمال مالية محددة ما زالت قرارًا مستقلاً.

في staging/production تُعرف البوابة من hostname المصرح. `X-Masal-Portal` بديل local/testing فقط. Cookies host-only مع أسماء جلسات مستقلة؛ `SESSION_DOMAIN=null`. Laravel يفرض حماية CSRF بالأصل الموثوق أو الرمز الصالح، ولا يسمح same-site عابرًا للبوابات. لا يرسل العميل دورًا لإثبات الوصول.

## السلوك المرجعي القديم المثبت في المصدر

المصدر: `frontend/legacy/src/services/access.js` و`engine.js` و`login-screen.js`. السلوك أدناه ليس سياسة منفذة تلقائيًا في Laravel.

- defaults ليست الصلاحيات الفعلية. localCan يفحص نشاط المستخدم وملف الصلاحيات والاستثناءات وصلاحية العرض؛ can يضيف قيودًا صلبة وفحص مسار الشبكة وقواعد المنع وصلاحيات المستخدمين الأعلى.
- الفرعي والفرع الفرعي يستخدمان sub. branchCreationBlocked يسمح بإنشاء الفرع فقط إذا كان والد الفرعي رئيسيًا؛ يمنع مستويات إضافية.
- digital.create وintegrations.transact محصورتان في pos للتنفيذ الفعلي؛ main/sub قد يفوضان ضمن قواعد canDelegate.
- sell.view/create/bulk/deliver/print/result/reprint محصورة في sub/pos أو موظف بدور إدارة مماثل، مع استثناء التفويض للرئيسي. لذلك owner ليس بائعًا تلقائيًا في السلوك الحالي.
- posTypes مقيد بدور الإدارة owner، وgovernorates بدور المستخدم owner.
- الخريطة مقيدة بـowner/employee/supervisor، ولها افتراضات إضافية تمنعها لبعض الأدوار افتراضيًا.
- نقطة البيع لا ترسل إشعارات ولا تنفذ تحويلات جماعية/اعتمادات/استيراد مالي.
- scope قد يعيد نطاقًا واسعًا لموظف النظام دون جذور مخصصة؛ يجب مراجعة هذا الافتراض قبل نقله.
- تعديل صلاحيات الذات أو المدير ممنوع؛ سبب التعديل إلزامي؛ لا منح لصلاحية أو نطاق لا يملكه المنفذ.
- engine.requirePermission وallowed يطبقان محليًا في المتصفح؛ هذا لا يحقق حماية سيرفر.

كتالوج الإجراءات الفعلي الافتراضي المستخرج آليًا محفوظ في PERMISSION_CATALOG.md. المخرجات من عينة اصطناعية لفحص الدوال، وليست من بيانات المستخدم أو المتصفح.

## قواعد السيرفر المستمرة عند نقل المجالات

لكل endpoint: auth + حساب فعال + إذن الإجراء + نطاق المورد + حالة وقواعد العملية. يجب فرض النطاق على queries والملفات والتصدير والتجميعات، وإعادة التحقق قبل commit في الإجراءات الحساسة.

- لا ثقة في role/account_id/parent_id يرسلها العميل.
- لا منح لصلاحية إلا إذا كانت قابلة للتفويض ولدى المنفذ والنطاق مصرحًا به.
- تغيير التبعية لا يعيد كتابة ملكية السجلات التاريخية أو ينقل الأرصدة تلقائيًا.
- الصلاحيات الحساسة مستقلة: التكلفة والربح وPIN والوثائق وأسرار التكامل.
- تعطيل الحساب/الأب وسحب الصلاحيات ينعكسان على الجلسات القائمة.
- عدم كشف الحقل يعني حذفه من استجابة API، لا إخفاءه في Vue فقط.

- [x] قراءات الحسابات وإنشاؤها بين شبكتين مستقلتين، ومنع الوكيل/POS من الأب والإخوة والجهات الخارجية؛ `AccountScopeTest` و`AccountCreationTest`.
- [x] رفض معرف أب/حساب خارج النطاق وحقول role/status/permissions ومحاولات النوع غير المسموح في APIs الأساس؛ لا كشف موارد خارج النطاق.
- [x] فرض بوابة المضيف ورفض عبور الجلسة وتجاوز العضوية؛ `PortalIsolationTest`.
- [x] الإيقاف وسحب الإذن والسلسلة الناقصة تمنع الطلب اللاحق رغم وجود جلسة سابقة؛ اختبارات الباك، واختبارات الواجهة تمنع بقاء هوية/قائمة قديمة وإحياء جلسة خرجت.
- [x] إنشاء account/user/membership/closure/audit ذري والتحقق من الأنواع والحقول والتكرار؛ `AccountCreationTest` و`AccountHierarchyTest`.
- [x] اختبارات تعديل وإيقاف وتفويض الدفعة الثانية ورفض الذات/الشبكة الأخرى والتزامن والمنع الأعلى؛ AccountManagementTest وStaffManagementTest وHTTP/MariaDB.
- [ ] نقل التبعية ما زال بلا API ويختبر عند تنفيذه.
- [x] المرفقات الخاصة والتنزيل ومنع IDs خارج الشبكة؛ AccountAttachmentTest وHTTP فعلي.
- [ ] التصدير والمجالات المقبلة تحتاج اختبارات مستقلة، ورفع صورة من UI لم يُنقر في هذا الفحص.
- [x] التابع لا يعدل الأب/الذات ولا يغير kind/role/parent أو يمنح نفسه نطاقًا خارج actor/employer؛ اختبارات الدفعة الجديدة.
- [ ] الموظف بصلاحية عرض لا يبيع أو يصدر رموزًا أو ينقل رصيدًا.
- [ ] منعه من حقل حساس يمنع الحقل في القائمة والتفاصيل والتقرير والملف.
- [ ] لا دور خاص أو حساب يتجاوز المنع المالي وحالة البطاقة لمجرد امتلاك صلاحية عامة.

## قرارات معلقة

بيع المدير والرئيسي مباشرة، تفويض المجالات المالية والمنتجات، حق الأب في تفاصيل أرباح/بطاقات التابع، الإيقاف التجاري الجزئي واستثناءات الدعم، العضويات المتعددة ونقل التبعية. حدود staff/profile لهذه الدفعة مثبتة في الجدول أعلاه؛ لا تعمم على المالية. إنشاء POS تحت كل مستوى وكيل حُسم ونُفذ؛ العضوية الواحدة والمنع عند تعطيل أي سلف مطبقان للأساس فقط. لا تقفل بقية القرارات على أساس السلوك القديم وحده.

حقول الحساب والموظف والمرفق توصف في العقد؛ كلمة المرور لا تدخل الاستجابة أو التدقيق، ولا تضاف بيانات PIN/مزود/ربح قبل تنفيذ صلاحيات حقولها. الصور والمستمسكات لها بوابة عرض مستقلة وتخزين خاص في هذه الدفعة. تفاصيل حقول الحسابات القديمة وقائمة نقل الإجراءات في [ACCOUNT_FEATURE_REVIEW.md](ACCOUNT_FEATURE_REVIEW.md).
