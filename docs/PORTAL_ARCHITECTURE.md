# بوابات ماسال الثلاث — أساس التنفيذ

تحديث 2026-10-06: البوابات النهائية `admin.dananir-iq.com` و`agents.dananir-iq.com` و`pos.dananir-iq.com` أصبحت فعّالة، والعمل على الاستضافة يستكمل عليها. الإصدار الخاص هو `20261006-final-domains-01` للحسابات والموظفين والصلاحيات والمرفقات والشركات والفئات وإتاحة التابعين، مع واجهة الدفعة الثالثة دون تعديل التصميم. اجتاز التحويل 138 فحص HTTP للروابط النهائية و9 فحوص لإيقاف كتابة بيئة التجربة، مع مطابقة 174 بصمة ملف مصدر وشهادات TLS صالحة. [دليل التحويل النهائي](FINAL_DOMAIN_CUTOVER.md)، و[دليل الدفعة الثالثة وحدودها](CATALOG_PHASE3_VERIFICATION.md). تشغيل الروابط النهائية لا يعني اكتمال نقل النظام؛ المخزون والبيع والمالية واللغات وبقية الوظائف ما زالت ضمن [حصر المشروع الأصلي](ORIGINAL_PROJECT_INVENTORY.md).

التاريخ: 2026-10-06، توقيت بغداد. هذه الوثيقة تعكس قرار المستخدم الأخير: ثلاث بوابات، وليست خمسة مواقع أو صفحة دخول موحدة. اسم المشروع «ماسال»؛ `dananir-iq.com` هو الدومين الذي قدمه المستخدم، وليس تغييرًا لاسم المشروع.

## الشكل المعتمد

| البوابة | مستخدموها | الرابط النهائي الفعّال |
|---|---|---|
| مدير النظام `admin` | مستخدمو حساب النظام المصرح لهم | `https://admin.dananir-iq.com/login` |
| الوكلاء `agents` | الرئيسي والفرعي والفرع الفرعي وموظفو حساباتهم | `https://agents.dananir-iq.com/login` |
| نقاط البيع `pos` | نقطة البيع وموظفو حسابها المصرح لهم | `https://pos.dananir-iq.com/login` |

السجل التاريخي: نشر الأساس أولًا على `admin-test.dananir-iq.com` و`agents-test.dananir-iq.com` و`pos-test.dananir-iq.com`. نجح دخول المدير وخروجه ثم دخوله ثانية، ولم تنتقل جلسته إلى المضيفين الآخرين؛ دليل تلك المرحلة وحدودها في [FOUNDATION_VERIFICATION.md](FOUNDATION_VERIFICATION.md) و[HOSTING_READINESS.md](HOSTING_READINESS.md). بعد التحويل، تعيد طلبات GET للواجهة على أسماء `-test` توجيهًا 302 إلى بوابتها النهائية، وترفض API وCSRF بالحالة 410. الباك القديم في وضع الصيانة وقاعدته وإصداره محفوظان للاستعادة، وليسا مصدر كتابة للتطوير الحالي.

لكل بوابة مدخل بناء مستقل، وصفحة دخول، وقالب لوحة وقائمة مناسبة. يوجد مصدر Vue مشترك للمكونات والخطوط والاتصال بالـAPI؛ لا تنسخ الوظائف المشتركة ثلاث مرات. يوجد Laravel واحد وقاعدة بيانات واحدة في هذه المرحلة.

## مكان الملفات

```text
masal-vue/
├── frontend/       مصدر Vue وإعدادات بناء البوابات
│   ├── src/        الواجهة الجديدة
│   └── legacy/     مصدر الواجهة السابقة للمراجعة أثناء النقل
├── backend/        Laravel ومخطط قاعدة البيانات واختباراته
├── contracts/      عقد API بين المشروعين
├── docs/           القرارات وحصر الوظائف ودليل المراجعة
├── deployment/     قوالب وإجراءات النشر
└── MIGRATION_PLAN.md
```

المصدر القديم داخل `legacy` مرجع مؤقت. لا تستورده البوابات الجديدة، ولا يُرفع عند نشرها. وجوده لا يعني أن وظائف البيع والمخزون وغيرها نُقلت بالفعل؛ إزالة كل وظيفة قديمة مرتبطة باكتمال بديلها واختبارها. لا حذف لبيانات المتصفح ضمن هذه الدفعة.

مسارات المصدر المحلي وترتيبه لم يتغيرا عند التحويل. على الاستضافة أصبحت ملفات التشغيل كالتالي:

```text
/home/dananiriq/
├── masal-backend/
│   ├── releases/20261006-final-domains-01/
│   ├── current -> releases/20261006-final-domains-01/
│   └── shared/
│       ├── .env
│       └── storage/
└── public_html/masal/portals/
    ├── admin/
    ├── agents/
    └── pos/
```

كل مجلد بوابة عام يحتوي بناء Vue وجسر API إلى `/home/dananiriq/masal-backend/current/public/index.php`؛ البيئة والتخزين وLaravel خارج الويب. قاعدة التشغيل الحالية `dananiriq_masalprod` نُسخت من staging، وطُوبق محتوى الجداول الثلاثين كاملًا عند النقل: حسابان ومستخدمان حقيقيان وشركة واحدة و28 فئة محفوظة. بقي `APP_KEY` وبيانات كلمات المرور كما كانت. لم يستبدل التحويل ملفات الدومين الأساسي `dananir-iq.com`. أدلة النسخ والمقارنة والتفعيل في [FINAL_DOMAIN_CUTOVER.md](FINAL_DOMAIN_CUTOVER.md).

## كيف يعمل العزل

1. المتصفح يفتح نطاق إحدى البوابات.
2. Laravel يحدد البوابة من اسم المضيف المطابق لإعدادات السيرفر، ثم يختار جلسة تلك البوابة.
3. تسجيل الدخول يتحقق من المستخدم والحساب ونوع الحساب ونشاطهما.
4. كل طلب بعد الدخول يفحص الجلسة وصلاحية الإجراء ونطاق الحساب وحالة الحساب والأسلاف.
5. Laravel يجلب البيانات داخل النطاق المسموح فقط. Vue تعرض النتيجة ولا تحدد نطاق الحماية.

لا يعتمد السيرفر على `portal` أو `role` أو `account_id` يرسله العميل لمنحه صلاحية. حساب نقطة البيع لا يدخل بوابة الوكلاء، وحساب الوكيل لا يدخل بوابة المدير. داخل بوابة الوكلاء يبقى الرئيسي والفرعي والفرع الفرعي أنواع حسابات مختلفة.

## الحساب ليس هو المستخدم

`accounts` يمثل جهة تجارية أو حساب النظام. `users` يمثل الأشخاص. `account_memberships` يربط الشخص بالحساب ودوره وصلاحياته. أنواع الحساب الأساسية:

| القيمة في API | المعنى | البوابة |
|---|---|---|
| `system` | حساب النظام | `admin` |
| `main_agent` | وكيل رئيسي | `agents` |
| `sub_agent` | وكيل فرعي | `agents` |
| `sub_branch` | فرع فرعي | `agents` |
| `pos` | نقطة بيع | `pos` |

الأصل هو `parent_id`، وجدول `account_closure` يسجل علاقة كل حساب بأسلافه وتابعيه. نطاق حساب المالك: نفسه وتابعوه فقط، ونقطة البيع نطاقها نفسها؛ موظف الحساب يخضع كذلك لجذور نطاقه وعلامة شمول التابعين. حساب النظام يحتاج صلاحية الإجراء حتى عند وجود نطاق عام. شمل الأساس الأول إنشاء حساب تابع ومستخدمه الأول وفق القواعد أدناه؛ أضافت الدفعة الثانية الصلاحيات المخصصة والموظفين وفق [مصفوفة الصلاحيات](PERMISSION_MATRIX.md)، بينما نقل التبعية ما زال غير متاح.

أكد المستخدم أن نقطة البيع يمكن أن تتبع الرئيسي أو الفرعي أو الفرع الفرعي مباشرة؛ لا تُلزم بوجود المستويات الثلاثة فوقها. وأكد إنشاء الحسابات داخل نطاق المنفذ وفق نوع الأب المختار:

| الأب المختار | أنواع الأبناء المسموحة |
|---|---|
| النظام | وكيل رئيسي |
| وكيل رئيسي | وكيل فرعي أو نقطة بيع |
| وكيل فرعي | فرع فرعي أو نقطة بيع |
| فرع فرعي | نقطة بيع |
| نقطة بيع | لا أبناء |

مع `account.create` يستطيع المدير إنشاء الحسابات داخل النظام، والوكيل تحت نفسه أو تابع فعلي داخل شبكته. مثال: الرئيسي ينشئ فرعًا فرعيًا تحت فرعي تابع له؛ لا ينشئه مباشرة تحت الرئيسي. لا إنشاء تحت أب أو أخ أو شبكة أخرى. تتكون العضوية والصلاحيات الافتراضية في السيرفر؛ لا يأخذ المسار `role` أو `permissions` أو `status` من العميل.

## الجلسات والـAPI

كل بوابة تتصل بمسار `/api/v1` على نطاقها نفسه؛ مثال: طلب الوكيل إلى `https://agents.dananir-iq.com/api/v1/auth/me`. لا تحتاج هذه الدفعة إلى نطاق API مشترك أو مشاركة كوكي بين النطاقات.

- `SESSION_DOMAIN=null`: كوكي الجلسة لا يُصدر بصفة `.dananir-iq.com`، ولا يشترك بين البوابات.
- لكل بوابة اسم جلسة مستقل يختاره السيرفر قبل بدء الجلسة. تستخدم `HttpOnly` و`Secure` في HTTPS و`SameSite=Lax`.
- يستخدم المتصفح `XSRF-TOKEN` القياسي، وهو أيضًا خاص بالمضيف نفسه، ويرسل قيمته بعد فك ترميز URL في `X-XSRF-TOKEN` عند الطلبات التي تغير الحالة.
- تبدأ جلسة الدخول بطلب `GET /sanctum/csrf-cookie` ثم `POST /api/v1/auth/login`.
- لا يصدر أساس الواجهة رمز Bearer، ولا تُحفظ الهوية أو بيانات الحسابات في `localStorage` أو `sessionStorage` أو `IndexedDB`.
- تجدد هوية المستخدم عبر `/auth/me` عند فتح التطبيق. الخروج يمسح حالة Vue من الذاكرة ويلغي الجلسة في السيرفر.

مسارات الأساس تسجل ضمن مجموعة `web` لجلسة وCSRF صريحتين، حتى لو كان شكل الرابط `/api/v1`. المسارات المحمية تستخدم `auth:sanctum` بالإضافة إلى فحص البوابة والحساب والنطاق. وضعها في مجموعة API عديمة الجلسات بدون إعداد stateful لا يحقق هذا التصميم. [آلية جلسات SPA في Sanctum](https://laravel.com/framework/docs/13.x/sanctum#spa-authentication).

Laravel 13 يتحقق أولًا من أصل الطلب عبر `Sec-Fetch-Site`: الطلب من الأصل نفسه يمكن أن يقبل دون فحص الرمز، وإلا يستخدم الرمز كبديل. لا نفعّل قبول `same-site` بين البوابات. الواجهة تستمر بتهيئة وإرسال XSRF للتوافق، واختبار المنع يستخدم طلبًا دون أصل موثوق ودون رمز صالح. [حماية تزوير الطلبات في Laravel 13](https://laravel.com/framework/docs/13.x/csrf).

تسجيل الخروج يتحقق من هوية الجلسة وربطها بالبوابة، ويظل متاحًا حتى بعد إيقاف الحساب لإبطال الجلسة؛ إيقاف الحساب يمنع `/auth/me` وطلبات البيانات.

## تحديد المضيف والتطوير المحلي

في الإنتاج توجد قائمة مضيفين محددة للبوابات. المضيف غير المعروف مرفوض، ولا يسمح wildcard. لا تُقبل ترويسة `X-Masal-Portal` لإثبات البوابة في الإنتاج. لا يُعتمد `X-Forwarded-Host` إلا بعد ضبط وسيط موثوق فعليًا؛ لا يُوثق أي وسيط عشوائي. [إعداد المضيفين الموثوقين في Laravel](https://laravel.com/framework/docs/13.x/requests#configuring-trusted-hosts).

للتطوير والاختبارات فقط، حيث البوابات تستخدم `localhost` نفسه، يمكن إرسال `X-Masal-Portal: admin|agents|pos` إلى السيرفر المحلي. هذا الاستثناء محصور في `local/testing`، ويُختبر رفضه في بيئة إنتاج. لا ينشأ منه مسار دخول إضافي في الاستضافة.

## ما غطته الدفعة الأولى — سجل تاريخي

- فصل المصدر والاعتماديات والبناء.
- مداخل البوابات الثلاث، والدخول والخروج وحالة الهوية.
- الحسابات والتبعية والعضوية وصلاحيتي `account.view` و`account.create`؛ نقطة البيع لا تمنح صلاحية الإنشاء.
- قائمة حسابات بصفحات وتفاصيل ضمن النطاق.
- إنشاء حساب ومستخدمه الأول وعلاقات الشجرة والتدقيق داخل معاملة واحدة؛ لا تظهر كلمة المرور في الاستجابة.
- اختبارات منع الدخول إلى بوابة أخرى والوصول لشبكة مستقلة وإيقاف الحساب.
- عقد API ودليل نشر قابل للمراجعة.

لا تعتبر هذه الدفعة انتقالًا مكتملًا للمخزون أو البيع أو المحافظ أو التقارير أو الدعم أو المزودين. صلاحيات المصدر السابقة لا تُنسخ تلقائيًا؛ تراجع حسب حصر الوظائف والقرارات المالية قبل تنفيذ كل مجال.

## المراجعة

- [ ] الدخول من البوابة الصحيحة ينجح.
- [ ] حساب البوابة الأخرى مرفوض دون إصدار جلسة مصرح بها.
- [ ] جلستا المدير والوكيل يمكن أن تتعايشا في متصفح واحد على نطاقين مستقلين.
- [ ] لا يرى الوكيل الأب أو الإخوة أو شبكة أخرى بتغيير المعرّف.
- [ ] نقطة البيع لا ترى نقطة أخرى.
- [ ] إنشاء تابع يطابق نوع الأب ويظل داخل النطاق؛ تغيير parent_id أو إرسال role/permissions/status لا يرفع الامتياز.
- [ ] إيقاف الحساب أو أحد أسلافه يمنع الطلب اللاحق وفق افتراض الأساس في `PHASE1_DECISIONS.md`.
- [ ] طلبات تغيير الحالة دون تحقق أصل موثوق ودون CSRF صالح مرفوضة؛ لا يسمح تلقائيًا بـsame-site بين البوابات.
- [ ] `.env` و`vendor` ومصدر Laravel غير مكشوفة عبر أي بوابة.
- [ ] لا توجد اعتماديات تشغيل جديدة على التخزين المحلي أو `legacy`.

هذه قائمة قبول عامة، وليست إعلانًا أن جميع البنود اختبرت في متصفح الاستضافة لكل دور. الأساس نُشر واختبرت مصادقته وعزل جلسة المدير وCSRF وفحوص المعاملات على MariaDB؛ أدلة كل حالة وحدودها في `FOUNDATION_VERIFICATION.md` و`MIGRATION_PLAN.md`. تشغيل البوابات النهائية مثبت الآن في [FINAL_DOMAIN_CUTOVER.md](FINAL_DOMAIN_CUTOVER.md)، بينما نقل بقية وظائف الأعمال والتصميم واللغات وفحص المسارات المترابطة بالكامل ما زال مطلوبًا وفق [حصر المشروع الأصلي](ORIGINAL_PROJECT_INVENTORY.md).
