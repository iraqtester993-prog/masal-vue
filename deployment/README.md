# نشر دنانير وصيانته

مرجع التشغيل الحالي **`20261018-permissions138`** بتاريخ 2026-10-18. يعمل النظام من مصدر واحد وقاعدة تشغيل مركزية واحدة؛ بوابات الويب وAndroid واجهات للنظام نفسه. تنظيم حزمة التسليم لا يستلزم استبدال القاعدة أو تغيير بياناتها.

## بنية الاستضافة

```text
/home/dananiriq/masal-backend/
├── releases/<release>/          Laravel واعتمادياته خارج الويب
├── current -> releases/...     النسخة الفعالة
└── shared/
    ├── .env                    البيئة الخاصة
    └── storage/                التخزين الدائم والخاص

/home/dananiriq/public_html/
├── masal/portals/admin/
├── masal/portals/agents/
└── masal/portals/pos/
                                موقع الشركة العام في جذر الدومين
```

قوالب الجسر والتوجيه في `cpanel/`. الجسر يصل إلى `masal-backend/current/public/index.php` ويحفظ مضيف البوابة. تعديل `.htaccess` يراعي إعداد PHP الذي تولده cPanel و`.well-known` والمحتوى القائم. المصدر والبيئة وقواعد البيانات والنسخ الخاصة لا توضع في جذر عام، ولا تنشأ وصلة عامة للمرفقات الخاصة.

المضيفون المعتمدون: `admin.dananir-iq.com` و`agents.dananir-iq.com` و`pos.dananir-iq.com`، و`dananir-iq.com` و`www.dananir-iq.com` لموقع الشركة. الجلسات host-only وSecure وHttpOnly على HTTPS. الموقع العام له قائمة API محدودة ولا يفتح حسابات الإدارة.

## البناء والحزمة

من المصدر المجمد، بعد تثبيت الاعتماديات:

```powershell
.\scripts\build.ps1 -Target all
```

ينتج بناء الواجهات الأربع. الأدوات الحالية تجهز الحزمة وتتحقق منها وتراجع الاستضافة؛ لا ترفع ملفات أو تفعل إصدارًا أو تحذف قواعد وملفات تلقائيًا:

```powershell
python deployment/package_release.py --help
python deployment/verify_release.py --help
python deployment/hosting_guard.py --help
```

`package_release.py` يجمع ملفات الإصدار من القائمة المعتمدة ويولد manifest ببصماتها. `verify_release.py` يراجع الحزمة ومحتوياتها مقابل البيان. `hosting_guard.py` يجري مراجعة ارتباطات وملفات الاستضافة وفق إعدادها المحدد. راجع `--help` وإعداد البيئة والبيان قبل اعتماد أية مخرجات؛ لا تستبدل الأداة تسلسل التفعيل المحروس أدناه.

مثال تجهيز حزمة في مجلد جديد خارج المصدر، ثم فحصها:

```powershell
python deployment/package_release.py RELEASE_NAME --output D:\deliveries\RELEASE_NAME --include-public
python deployment/verify_release.py D:\deliveries\RELEASE_NAME --manifest-sha256 TRUSTED_SHA256
python -m unittest discover -s deployment/tests -v
```

حدد اسم إصدار فعليًا، وأنشئ المجلد الأب فقط؛ الأداة ترفض مجلد إخراج موجودًا أو داخل المصدر. استبدل `TRUSTED_SHA256` ببصمة manifest المستلمة من مرجع مستقل. ملفات البيئة والتخزين والاعتماديات والكاش والاختبارات وقواعد البيانات لا تدخل حزمة النشر. يفحص التحقق جميع الملفات وCRC للضغط دون فك الأرشيف إلى مسارات النظام.

على الاستضافة، باستخدام manifest موثوق وبصمته:

```bash
python3 deployment/hosting_guard.py \
  --backend-root /home/dananiriq/masal-backend \
  --web-root /home/dananiriq/public_html/masal/portals \
  --expected-release RELEASE_NAME \
  --expected-database dananiriq_masalprod \
  --manifest /private/RELEASE_NAME/manifest.json \
  --manifest-sha256 TRUSTED_SHA256
```

أضف `--public-root /home/dananiriq/public_html` إذا احتوى البيان الموقع العام. هذه الأداة تفحص مؤشر الإصدار وبصمات الملفات وتعرض الملفات الزائدة والمحتوى المتطابق للقرار؛ لا تحذفها ولا تفعّل إصدارًا. مقارنة اسم القاعدة فيها **سياسة متوقعة فقط** وتطبع `database_checked=false`؛ لا تتصل بقاعدة البيانات ولا تنفّذ ملف config. فحص القاعدة الفعلية منفصل عبر `cpanel/audit_database.php` مع بصمة config المثبتة وخياراته المعتمدة.

لفحص قاعدة التشغيل للقراءة فقط، من مجلد الأدوات الخاص على الخادم وباستخدام PHP المتوافق:

```bash
php deployment/cpanel/audit_database.php \
  --backend-root /home/dananiriq/masal-backend \
  --expected-release 20261018-permissions138 \
  --expected-database dananiriq_masalprod \
  --config-sha256 TRUSTED_CONFIG_SHA256
```

يُستبدل اسم الإصدار بما اعتمد فعليًا، وتُستلم بصمة `bootstrap/cache/config.php` من سجل تجهيز موثوق؛ لا تطبع محتوى config للحصول عليها. الأداة تعمل من CLI فقط، وتفحص بصمة config قبل تحميله وتستخدم معاملة PDO للقراءة فقط وأقفال التنسيق. مخرجاتها بصمات الجداول والمخطط والمشغلات ونتائج القيود، دون كلمات مرور أو تفاصيل أرصدة. لا تضع أداة المراجعة في جذر الويب.

ملفات النشر تبنى من قائمة صريحة وبصمات للمحتوى؛ لا ترفع مجلد العمل كاملًا. تثبت اعتماديات الإنتاج من `composer.lock` دون أدوات التطوير، وتتحقق متطلبات المنصة باستخدام PHP المستخدم في الويب وCLI.

حزمة Backend تنقل الملفات المصدرية فقط. عند تجهيز إصدار جديد، أنشئ `bootstrap/cache` بصلاحية كتابة مناسبة، واربط التخزين الدائم وجهّز مجلداته قبل تثبيت Composer واكتشاف الحزم وتوليد الكاش؛ لا تستخدم صلاحيات `777`.

## تسلسل النشر

1. حدد المسار الحالي وقاعدة التشغيل الفعلية ونسخ الواجهات، وسجل مخطط القاعدة وبصمات الملفات ومؤشرات سلامة البيانات.
2. خذ نسخة حديثة متسقة من القاعدة والباك والتخزين والبيئة وملفات الويب المتأثرة. نزّلها إلى الأرشيف الخاص وتحقق من البصمات ومحتوى الأرشيف وقابلية استرجاعه.
3. جهز نسخة Backend جديدة في مسار خاص، من الحزمة المجمدة. اربط البيئة والتخزين المشتركين مع حفظ `APP_KEY`، ثم افحص PHP والكاش والمسارات والصحة دون تنفيذ عمليات أعمال.
4. جهز أصول الويب قبل تفعيل مداخلها، مع إبقاء الملفات التي يحتاجها الإصدار القائم. قارن الملفات مع manifest؛ اختلاف ملفات غير معتمدة يوقف النشر للمراجعة.
5. فعّل النسخة الحالية ومداخل الويب بصورة محروسة وبإيصال استرجاع. احتفظ بخطة رجوع متوافقة مع مخطط القاعدة؛ رجوع الملفات وحده لا يعكس migration غير متوافق.
6. افحص HTTPS وAPI وCSRF وعزل المضيفين والنطاقات والأصول، وطابق بيانات التشغيل والمخطط قبل وبعد. لا تنشئ بيعًا أو تمويلًا أو شراء مزود للاختبار في الإنتاج.
7. أرشف نسخة الرجوع وأدلة التفعيل خارج المسارات العامة، وتحقق من النسخة المنزلة قبل تنظيف المؤقتات والملفات القديمة المسموح بها.

مراجعة migrations قرار مستقل داخل الحزمة؛ لا تشغلها تلقائيًا لمجرد نشر ملفات. `migrate:fresh` والبذر التجريبي وحذف جداول ليست خطوات تحديث نظام قائم. فحوص الاستعادة وMariaDB الأصلية تستعمل بيئة ظل منفصلة، ولا تختبر على قاعدة التشغيل.

## تنظيم الملفات ومنع التراكم

الإصدارات السابقة وحزم المراجعة والنسخ الاحتياطية تنتقل إلى الأرشيف الخاص بعد تحقق كامل. تنظيف أصول الواجهة يعتمد مراجع المداخل وService Worker وقائمة الإصدار، مع مراعاة العملاء المفتوحين؛ اختلاف hash لا يعني أن الملف مهمل. يحتفظ APK المعتمد ومسارات التنزيل العامة التي لا تزال مستخدمة حتى قرار إحلالها.

لا تُنشأ قاعدة staging أو verify لمجرد نشر الواجهة. أي قاعدة اختبار مستقبلية يلزم أن يكون لها غرض ومالك ونطاق وموعد إلغاء واضح، وتبقى منفصلة عن قاعدة التشغيل. لا تحذف قاعدة أو ملفًا بالاسم وحده قبل التحقق من ارتباطاته وأخذ نسخته.

تنظيف ملفات النشر لا يشمل التخزين الخاص أو سجلات الأعمال أو حسابات النظام. النسخ المتولدة داخل وظيفة النسخ في التطبيق لها سياسة احتفاظ خاصة؛ لا تمسحها أداة إزالة أصول الويب.

أداة [إزالة تكرار المحتوى الثابت](cpanel/IMMUTABLE_ASSETS.md) تحفظ جميع روابط الملفات، وتشارك البايتات المتطابقة فقط بعد مطابقة الملكية والصلاحيات ووقت HTTP. تشغيلها يمر بخطة مثبتة وأرشيف محقق خارج الاستضافة وإيصال تحقق قبل التطبيق، مع مسار استرجاع. تعمل على Python 3.9 فأحدث، ولا تتصل بقاعدة البيانات أو تنفذ نقلًا أو نشرًا آليًا.

## المهام والاسترجاع

تحقق من cron على المسار `current/artisan` ومن إصدار PHP الصحيح، ومن تنفيذ `schedule:list` والمهام الفعلية. مهام `backups:work` وصيانة المرفقات لها شروط تشغيلها وأقفالها. وجودها في الشفرة لا يثبت أن cron مهيأ.

الاسترجاع إجراء محروس إلى قاعدة منفصلة بعد معاينة النسخة والتأكد من المفاتيح والقيود والعمليات الرقمية المعلقة. إعادة ملفات إصدار سابق لا تساوي استعادة قاعدة. اعتمد دليل التشغيل الخاص وأدلة الظل المقبولة، وسجل أي تحول فعلي مع سبب ومسؤول.

التحقق الآلي لا ينشر إلى الاستضافة أو Git. أسرار SSH وDB والمزودين وتوقيع Android لا تدخل قوالب النشر أو manifest العامة. [دليل التسليم](../docs/HANDOVER.md) يحدد ما يُسلّم بصورة محمية، و[فهرس الأرشيف](../docs/ARCHIVE_INDEX.md) يحدد موضع الأدلة.

`signed_release.ps1` يفحص خزنة توقيع Android المشفرة بملف فتح خاص، ولا يبني افتراضيًا. خيار `-Build` يبني Release باستخدام مفتاح مؤقت، دون نشره. هذه وظيفة توقيع APK منفصلة عن تجهيز حزمة ملفات الاستضافة، وتبقى بيانات الفتح خارج المصدر.
