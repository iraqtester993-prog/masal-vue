# نشر وصيانة ماسال على cPanel

الحالة بتاريخ **2026-10-07**: الباك **`20261007-full-system-07`** والواجهة **`20261007-full-system-07-ui01`** منشوران وفعالان على بوابات المدير والوكلاء ونقاط البيع والموقع العام. نجح القبول المعزول على MariaDB واستعادة cPanel المباشرة والعامل الكامل، ثم تطابق ملفات النشر الـ609 وحفظ بيانات التشغيل و**1746/1746 فحص HTTP**. فُحص نموذج الربط على الحاسبة بالمظهرين وعلى الهاتف وأُنشئت نسخة موقعة حية؛ القبول البصري الشامل والبيع الخارجي والطباعة والبريد لها بنود مراجعة مستقلة. [خطة التنفيذ](../MIGRATION_PLAN.md) و[سجل التحقق النهائي](../docs/FULL_SYSTEM_07_VERIFICATION.md) مرجع الحالة. [سجل 06b](../docs/SALES_SUPPORT_REPORTS_VERIFICATION.md) و[سجل قطع الدومينات](../docs/FINAL_DOMAIN_CUTOVER.md) أدلة تاريخية.

```text
/home/dananiriq/masal-backend/
├── releases/<release>/          Laravel وvendor، خارج document root
├── current -> releases/...     الإصدار الذي يستخدمه الجسر
└── shared/

├── masal/portals/admin/         بناء Vue + .htaccess + masal-api.php
├── masal/portals/agents/
└── masal/portals/pos/
                                public منشور في جذر الدومين الأساسي
/home/dananiriq/masal-backups/   نسخ التشغيل خارج الويب
```

`current` يشير حاليًا إلى `releases/20261007-full-system-07`. الموقع العام يعمل من `/home/dananiriq/public_html/` بمحتوى الشركة الأصلي المنشور عبر حفظ مدقق، نسخة محتوى 2. مصدر التطوير `C:\Users\PRO\Desktop\masal-vue` مستقل عن الإصدارات المنشورة. لا ترفع `frontend/legacy` أو مصدر Vue أو `.env` أو قاعدة بيانات أو مجلد Laravel إلى الويب. لا تنشئ `storage:link` عامًا للمرفقات الخاصة.

دليل النشر الحالي: **PHP 8.5.11، Laravel 13.34، 94 جدول InnoDB، تطابق 609 ملفات**. حفظت بيانات **59 جدول أعمال سابقًا**، وبقي حسابان ومستخدمان دون استبدال ببيانات اختبار. تفاصيل النسخ والبصمات والفحوص النهائية في سجل 07.

## الجسر والمضيف العام

القوالب المعتمدة: [cpanel/masal-api.php](cpanel/masal-api.php)، و[cpanel/portal.htaccess](cpanel/portal.htaccess)، و[cpanel/public.htaccess](cpanel/public.htaccess). الملفات الفعلية بعد مطابقتها مع البيئة هي المرجع؛ أمثلة الدليل لا تستبدلها. الجسر يمرر إلى المسار الثابت `/home/dananiriq/masal-backend/current/public/index.php` ويحفظ المضيف والمسار الأصليين، ويحذف ترويسة اختيار البوابة القادمة من العميل.

المضيفون المصرحون: `admin.dananir-iq.com` و`agents.dananir-iq.com` و`pos.dananir-iq.com`، مع `dananir-iq.com` و`www.dananir-iq.com` للموقع العام. إضافة المضيف العام لا تمنحه API إداريًا. الجسر و`ResolvePortal` يفرضان عليه القائمة التالية:

| الطريقة | المسار | الاستخدام |
| --- | --- | --- |
| GET | `/api/v1/company/public` | محتوى الشركة العام المعتمد. |
| GET | `/api/v1/company/public/assets/<asset-uuid>` | أصل عام مصرح بعرضه. |
| GET | `/sanctum/csrf-cookie` | تجهيز CSRF. |
| POST | `/api/v1/company/inquiries` | حفظ استفسار بعد CSRF والتحقق وحدود الطلبات. |

بقية طلبات API على المضيف العام ترفض؛ لا تضف APIs الدخول والحسابات إلى قائمته. أخطاء API لا تتحول إلى HTML الخاص بـVue، وأصول `assets/` المفقودة تعيد 404. حافظ على إعداد PHP الذي تولده cPanel وعلى `.well-known` عند دمج `.htaccess`. لا تستبدل ملفات جذر الدومين القائم دون نسخة ومراجعة محتوياتها.

## متطلبات البيئة

- PHP للويب وCLI متوافق مع `composer.lock`، بحد فعلي **8.4.1+**؛ البيئة المستعملة `ea-php85`. نفذ `composer check-platform-reqs` على الإصدار نفسه؛ لا تتجاهل متطلبات المنصة.
- MariaDB/MySQL بمحرك **InnoDB** للجداول التشغيلية. المعاملات والأقفال والمشغلات تحتاج قبولًا على المحرك الفعلي، وليس SQLite وحده.
- HTTPS صالح، ومعالجة PHP في جذور الويب، ووصول الجسر إلى Laravel الخاص، وصلاحيات كتابة محدودة لـ`storage` و`bootstrap/cache` دون `777`.
- `APP_ENV=production` و`APP_DEBUG=false`، و`APP_KEY` الحالي محفوظ عند تحديث نسخة قائمة.
- مضيفو `backend/config/portals.php` والبيئة يطابقون DNS والجسر. `SESSION_DOMAIN=null`، وCookies الجلسة host-only مع Secure وHttpOnly وSameSite=Lax.
- `X-Masal-Portal` مساعد محلي/اختباري فقط؛ الإنتاج من أصل كل بوابة نفسه، دون CORS بين البوابات.
- أسرار DB والمزودين والنسخ تبقى خاصة؛ لا مفاتيح أو كلمات مرور في Vue أو Git أو بيانات اختبار الإنتاج.

## التحقق ثم تجميد الحزمة

من جذر المصدر على بيئة تطوير مستقلة:

```powershell
npm --prefix frontend ci
npm run frontend:test
npm run backend:test
& ./scripts/backend.ps1 vendor/bin/pint --dirty --format agent
npm run build
```

الأمر الأخير يبني **admin وagents وpos وpublic**. `npm --prefix frontend run build` يبني البوابات الثلاث فقط؛ أضف `npm --prefix frontend run build:public` للموقع العام. نتائج النسخة المنشورة: **SQLite: 561 حالة، 557 نجاحًا، 4 حالات تخطٍ، 5055 تأكيدًا؛ MariaDB: الأعداد نفسها و5057 تأكيدًا؛ Vue: 154 نجاحًا وأربعة أبنية ناجحة**. القبول المعزول المباشر لـcPanel نجح **باختبار واحد و34 تأكيدًا**، والعامل الكامل **باختبار واحد و68 تأكيدًا**. الحالات المتخطاة في المجموعة العامة لا تعد نجاحًا؛ سجل التحقق يحفظ أدلة القبول المنفصلة. لا تعتمد مصدرًا تغير بعد الفحص على نتيجة حزمة سابقة.

يجب أن يجتاز المصدر المجمد الفحص المحلي الكامل والفحص المعزول على MariaDB وفحوص المنصة والقيود المالية والنطاق والخصوصية. فحص استعادة cPanel المباشر والعامل الكامل يستخدم قاعدة وبيئة ظل منفصلتين فقط. بعد القبول استعمل أرشيف الباك نفسه الذي اختُبر، بدل جمع ملفات عمل قد تكون تغيرت.

مثال تجهيز دون رفع أو تفعيل، من جذر المشروع:

```powershell
$taskBackendSnapshot = 'C:\path\to\accepted-immutable-backend.tar.gz'
python deployment/build_staging_bundle.py RELEASE_NAME `
  --environment production `
  --backend-snapshot $taskBackendSnapshot `
  --include-public
```

استبدل الاسم والمسار بالحزمة المقبولة فعليًا. `--include-public` يضيف الموقع العام ويعمل مع `production` فقط. دون `--environment production` تستخدم الأداة staging افتراضيًا.

المخرجات داخل `deployment/.local/bundles/RELEASE_NAME/`:

- `backend.tar.gz`: مصدر الباك المجمد دون `.env` أو vendor أو storage أو بيانات اختبار.
- `portals.tar.gz`: ملفات البوابات الثلاث المبنية والجسر وقواعد التوجيه.
- `public-site.tar.gz`: الموقع العام عند استعمال `--include-public`.
- `manifest.json`: بصمات الأرشيفات والملفات والبيئة والمصدر الأصلي.

الأداة ترفض استبدال مجلد حزمة موجود ولا تنشر تلقائيًا. راجع manifest ومحتويات الأرشيفات والمضيفين قبل الرفع. تثبت اعتماديات الإنتاج من `composer.lock` أو تستخدم vendor متحققًا مطابقًا له، مع فحص متطلبات المنصة.

## إجراء التفعيل

1. سجل النسخة الحالية وبصماتها ومخطط DB، وخذ نسخة حديثة للقاعدة والباك والبوابات والتخزين وجذر الموقع. تحقق من التنزيل والبصمات وقابلية القراءة؛ احتفظ بالمصدر القديم و`APP_KEY`.
2. ارفع الحزمة المقبولة إلى `releases/<release>` خاص جديد، واربط `.env` وstorage من shared. لا تكتب فوق الإصدار الفعال ولا تنقل ملفات خاصة إلى الويب.
3. راجع migrations والرجوع. قبل تغيير مخطط التشغيل أوقف دخول الكتابات الجديدة، واستعمل صيانة مضبوطة وقفل runtime للانتظار حتى تنتهي المعاملات القائمة. العمليات الرقمية غير المحسومة تحتاج تحققًا مستقلًا؛ الصيانة لا تسحب شراء أُرسل إلى مزود.
4. نفذ migrations تحت إجراءات النشر المحروسة، وافحص المحرك والمشغلات والبيانات المحفوظة. لا `migrate:fresh` أو fixtures أو حذف جداول على بيانات العمل.
5. جهز الكاش الإنتاجي، ثم فعّل `current` والبوابات والموقع العام بصورة مضبوطة مع حفظ ملفات جذر الدومين وإعدادات cPanel. تحقق من صحة العملية والقاعدة الفعليتين قبل إعلان التفعيل.
6. افحص HTTPS وAPI وCSRF وعزل كل بوابة وصلاحيات الموظفين والشجرة والأصول العامة والخاصة. طابق بصمات الملفات وبيانات التشغيل، ثم افتح الكتابات بعد نجاح الفحص المحروس.
7. تحقق من scheduler والتكاملات والطباعة ضمن حدود الاختبار الحقيقي؛ لا شراء مزود أو استعادة إنتاج أثناء QA. سجل الأدلة والقيود في الخطة وسجل التحقق.

الرجوع للملفات وحدها لا يعكس migration غير متوافق. استعادة DB وظيفة مختلفة عن نشر الكود، تتطلب مراجعتها وتحقيقها وقفلها بدل استبدال القاعدة الحية.

## النسخ والاستعادة والمهام الخلفية

وحدة النسخ تحفظ لقطة خادم موقعة ومشفرة من DB المحددة والملفات الخاصة، دون البيئة أو APP_KEY أو جلسات قديمة. معاينة الرفع محدودة بـ**15 MB**؛ نسخة الخادم يمكن قراءتها بالتدفق إذا كانت أكبر. JSON التخزين المحلي القديم ليس تنسيق استعادة خادم مقبولًا.

الاستعادة لصاحب النظام وبصلاحياتها، وبعد معاينة ومراجعة كلمة المرور والنسخة الحالية. العامل ينشئ قاعدة scratch ويتحقق من المراجع والمشغلات والقيود، يأخذ نسخة أمان حديثة قبل التحويل، ويستعمل بوابة الكتابة والصيانة والتحويل المحروس والرجوع عند الفشل. العمليات الرقمية المعلقة تمنع التحويل؛ الاستعادة لا تعيد شراء بطاقات. تبطل الجلسات المتذكرة والحضور المتصل مع حفظ التاريخ. **جاهزية الاستعادة على الاستضافة تتطلب تهيئة المزود والعامل وقبول الظل الفعلي؛ الزر والاختبارات المحلية لا يثبتان ذلك.**

`BACKUP_PLATFORM_CLASS` افتراضيًا مزود غير متاح. تهيئة `CpanelRestorePlatform` ومفاتيحه تتم في البيئة الخاصة بعد قبول cPanel المعزول؛ لا تغير المفتاح أو القاعدة يدويًا لتجاوز شرط غير محقق.

`backend/routes/console.php` يسجل تنظيف مرفقات الدعم كل ساعة و`backups:work` كل دقيقة مع منع التداخل. تحقق النشر الحالي فعليًا من `schedule:list` على الإنتاج ومن cron كل دقيقة بقفل `flock`. cron القائم يحفظ ويفحص بدل استبداله دون مراجعة. قبول العامل الكامل تم في الظل المعزول؛ لم تُنفذ استعادة إنتاج أثناء QA. عند أي صيانة لاحقة تحقق من PHP الصحيح ومسار `current/artisan` وسجل التنفيذ؛ وجود المهمة في المصدر وحده لا يثبت تشغيلها.

## قبول النشر والأسرار

القبول النهائي يثبت تحميل صفحات البوابات وتحديثها، رفض عبور الحسابات والمضيفين، حدود الموظفين والشجرة، JSON لأخطاء API، 404 للأصول المفقودة، منع كشف `.env` وvendor والملفات الخاصة، حماية POST وCSRF، والقائمة المحدودة للمضيف العام. راجع الشاشات والأزرار والألوان والتخطيط في المتصفح؛ البناء لا يثبت مطابقة الأصل بنسبة 100%.

GitHub Actions الحالي **للتحقق فقط**، دون نشر إلى cPanel أو GitHub Pages. نشر لاحق يحتاج إعدادًا منفصلًا وبصمة SSH ومفاتيح داخل Secrets وبيئة نشر محكومة. المفاتيح الخاصة وكلمات المرور لا تدخل هذه الملفات أو manifest.
